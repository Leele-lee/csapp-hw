## thread

only one thread: read_thread
fgets call `pthread_cond_timedwait(&cond, &mutex, &ts) == ETIMEDOUT`  and wait for condition: either from read_thread receive signal of input(`pthread_cond_signal()`) or from fgets timeout

Besides: `pthread_cond_timedwait` always has fake wake up, so
we often using this while loop and `done` signal:

```c
pthread_mutex_lock(&mutex);
while (!done) {
    if (pthread_cond_timedwait(&cond, &mutex, &ts) == ETIMEDOUT) {
        done = 2;
        break;
    }
}
pthread_mutex_unlock(&mutex);
```

to guarantees that:

- The done flag has been truly set by the reader or timeout,
- You’re not reacting to a phantom wakeup.

## notice

```c
if (done == 2) {
        pthread_cancel(tid);
        pthread_join(tid, NULL);
        return NULL;
```

> I use this and run, the program didn't stop after 5 secs unless I print something

Your program didn't stop after 5 seconds unless you typed something because `fgets()` is a *blocking* call—it waits for user input before it returns. Even if the timeout occurs in your `tfgets` function, the thread running `fgets()` is still blocked in `stdin` until input is received.

Although you call `pthread_cancel(tid)` after a timeout, cancellation of a thread blocked in a standard I/O function like `fgets()` **won’t be immediate or even possible on some platforms**, especially on macOS. The cancellation only works if the thread reaches a cancellation point—and `fgets()` is not guaranteed to be one on all systems.

### Why This Happens

* `pthread_cond_timedwait()` *does* timeout correctly and sets `done = 2`.
* Your main thread then calls `pthread_cancel()`, but that only works if the target thread hits a cancellation point.
* On macOS, `fgets()` may not be a cancellation point or may block in a way that makes it unresponsive to cancellation.


> but after I delete pthread_join(tid, NULL), it worked

Let’s break down why **removing `pthread_join(tid, NULL)` made your program behave as expected**:

---

### 🔧 **What `pthread_join()` Does**

* It **waits for the target thread to terminate**.
* If the read thread is stuck in a `fgets()` call (i.e., waiting for input), then calling `pthread_join(tid, NULL)` **blocks the main thread** until that read thread exits.
* So even if your `tfgets` function detects a timeout and tries to return, the main thread is stuck **waiting for the read thread**, which won’t exit until you press Enter (because `fgets()` is blocking).

---

### ✅ What Happens When You Remove `pthread_join()`

* After a timeout, `tfgets` cancels the read thread (`pthread_cancel(tid)`).
* Without `pthread_join()`, your main thread **does not block** and returns immediately.
* This gives you the desired timeout behavior.

---

### ⚠️ Why This Is Risky

Removing `pthread_join()` leaves the **read thread detached and potentially dangling**:

* If cancellation is **delayed or ignored** (common with `fgets()`), the read thread could linger and cause **resource leaks** or **undefined behavior**.
* It’s generally good practice to clean up threads with `pthread_join()` or `pthread_detach()`.

---

### ✅ Recommended Fix

If you want to keep the timeout behavior *and* avoid leaks, use:

```c
pthread_cancel(tid);
pthread_detach(tid);  // do not block; safely lets the system clean up the thread
```

Replace:

```c
pthread_cancel(tid);
pthread_join(tid, NULL);
```

With:

```c
pthread_cancel(tid);
pthread_detach(tid);
```

---

### ✅ Summary

| Behavior                 | `pthread_join()` | No `pthread_join()` |
| ------------------------ | ---------------- | ------------------- |
| Waits for thread cleanup | ✅                | ❌                   |
| Returns after timeout    | ❌ (blocks)       | ✅                   |
| Safe from resource leaks | ✅                | ❌ (unless detached) |
